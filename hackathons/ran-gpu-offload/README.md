# North Carolina State University Hackathon 2026 — Topic 1: 32-Antenna Sensing with CUDA SRS Estimation

## Problem Statement

A monolithic OAI gNB with 32 antennas receives the 4-port SRS of a 4-antenna OAI UE over the
rfsimulator. The radio channel between them is a ray-traced street canyon (Sionna RT), replayed by
the rfsimulator as a CIR database. Sensing (locating the UE and the walls, tracking what moves)
needs a far better estimate of that channel than communication does. The gNB's fixed-point SRS
estimator is not precise enough.

## Objective

Write a GPU SRS estimator that is precise enough to enable tracking and sensing.

## Scope

Participants only implement the GPU-based SRS channel estimator in `srs_est_cuda.cu`.

The following are **out of scope**:

- The ray-traced channel and CIR database
- The UE/gNB PHY and MAC configuration
- The glue code and loader
- Sensing and localization algorithms
- The evaluation script

## Tasks

Tasks are outlined in the
[implementation guide](https://github.com/ConnorBlasie/openairinterface5g/blob/isac-task/doc/isac_srs_implementation_guide.md).
The suggested order is:

1. Build the reference ray-tracing binaries and the OAI code base.
2. Run and measure the fixed-point baseline.
3. Implement the CUDA SRS estimation, then measure it against the unit test.
4. Run the CUDA SRS `nr_srssim` precision gates.
5. Run the CUDA SRS end-to-end rfsim.
6. Score the run!

## Expected Result

- CTest cases go from failing to passing once the GPU implementation achieves enough precision to sense.
- The console output shows the CUDA module in use, with no fallback to fixed point.
- The RFsim test case connects gNB ↔ UE and shows a stable connection.
- `nmse.py` shows:
  - Median NMSE below **-30 dB** (the fixed-point estimator gets about -24 dB at 20 dB SNR)
  - `snr_db_median` of about **20 dB**
  - Fitted `gain_db` of about **50 dB or more**, steady from record to record (a sanity check only, not scored)

## Validation / Evaluation

Final performance is based on the NMSE (in dB) of the logged SRS estimates relative to the
synthetic channel generated by the ray-tracing library.

**Primary metric**

- Median NMSE (generated by the post-processing script) over the duration of the run
  (500 snapshots minimum).

**Secondary metrics**

- `nmse_db_p90` and `nmse_db_p10` (consistency across the run)
- The number of `test_srs_est` and `nr_srssim.module1`–`5` cases that pass
- GPU performance (reported, used as a tie-breaker): the mean and worst-case time per
  `srs_est_run()` call, measured with `cudaEventRecord` or `nsys`

## Deliverables

Participants should submit the following:

1. `srs_est_cuda.cu`, either as the full file or as a patch.
2. The `nmse.json` file from your end-to-end run (at least 500 records).
3. A `README.md` covering:
   - **Approach:** your algorithm (for example, delay-domain windowing or LMMSE), how you separate
     the cyclic-shift ports, and your kernel design
   - **Build & Test:** your exact build flags, GPU model, CUDA version, and the commands you ran
   - **Results:** the unit test and `nr_srssim` results, the `nmse.json` summary, and GPU timing per SRS
   - **Challenges:** what went wrong and how you fixed it
   - **Plots/visuals (optional):** for example, NMSE over time, the delay profile, or a street reconstruction
   - **Links:** your repository or fork and branch
   - **AI tools used:** which models or assistants you used (if any) and what for

For an example of a good write-up, see this
[Devpost project](https://devpost.com/software/finquest-9vso4m).
